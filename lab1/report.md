## 一、项目概况

### 1.1 要解决的问题

线下二手交易信息分散，买卖双方沟通成本高，缺少统一的发布、预约、审核与举报机制，交易过程缺乏留痕与可信保障。本系统提供一个二手商品发布、预约、线下交易的平台，规范交易流程，保障买卖双方权益。

### 1.2 项目目标

- 支持买家、卖家、管理员三类用户（外加游客）的注册、登录与权限管理。
- 支持商品草稿、提交审核、发布、修改、下架、违规处理的完整生命周期。
- 支持买家预约、卖家确认、交易完成，并正确处理并发预约、重复预约、旧页面操作等异常。
- 提供检索、统计、操作日志、举报处理、数据备份等运营能力。

### 1.3 系统范围

- 覆盖：注册登录、商品管理、预约交易、查询统计、举报处理、日志审计、数据备份与恢复。
- 明确不实现（对应 REQ-029）：短信验证码登录、微信/QQ 第三方登录、图形验证码、实名认证与身份证照片、在线支付、物流。预约不涉及下单与付款，只记录线下当面交易。

## 二、整体业务分析

### 2.1 主要业务流程

1. **注册登录**：手机号 + 昵称 + 密码注册，注册完成即为买家；登录仅支持"手机号 + 密码"。
2. **商品发布**：草稿 → 提交审核 → 待审核 → 已发布（审核未过退回草稿）。
3. **预约交易**：买家预约 → 卖家确认（附见面时间地点）或拒绝 → 线下交付 → 卖家点"已给货" → 买家点"确认收货" → 交易完成。
4. **违规处理**：用户举报 → 管理员受理 → 警告 / 判违规（商品转违规，在途预约终止）→ 卖家可申诉一次。

### 2.2 主要数据及关系

| 数据 | 关键字段 | 约束与关联 |
| --- | --- | --- |
| 用户 | 手机号、昵称、密码、角色、账号状态 | 手机号唯一、用户名唯一；卖家不独立建号 |
| 商品 | 名称、描述、价格、成色、状态、分类 | 一件商品挂一个二级分类；名称可重复 |
| 分类 | 两级分类 | 非空分类不可删只能停用 |
| 预约记录 | 编号、商品、买家、卖家、状态、时间、成交价、请求编号、版本号 | 同一商品仅一条进行中预约；成交价单独存储 |
| 日志 | 操作者、时间、对象、内容、改前、改后、原因 | 只追加不可改删 |

### 2.3 业务状态与状态转换

商品共七种状态：草稿、待审核、已发布、已预约、交易完成、已下架、违规。

| 当前状态 | 允许转换 | 禁止转换 |
| --- | --- | --- |
| 草稿 | → 待审核（提交审核） | — |
| 待审核 | → 已发布（审核通过）；→ 草稿（审核驳回） | — |
| 已发布 | → 已预约（被预约）；→ 已下架（卖家下架）；→ 违规（判违规） | — |
| 已预约 | → 交易完成（双方确认）；→ 已发布（买家取消/卖家拒绝/超时） | 不能直接下架、不能改价改描述 |
| 已下架 | → 待审核（重新提交审核） | 不能直接上架 |
| 违规 | 终点（申诉通过恢复为已下架） | — |
| 交易完成 | 终点 | 不能改回 |

核心规则：草稿须审核才能上架；上架后可下架、下架后须重新审核；已预约不能下架。

### 2.4 数据一致性

- 关联变更（预约/取消/拒绝/确认/判违规/封号/审核）在同一事务内完成，中途失败整体回滚。
- 预约占坑与商品状态强一致；统计数字允许延迟，五分钟内对账一致。

## 三、实验总结

### 3.1 访谈中的困难及解决方法

- 甲方用口语描述权限与状态，容易遗漏细节：通过第二轮跟进沟通（INT-02）补充预约记录字段、一致性联动、举报时限、备份策略等内容。
- 状态转换规则复杂：整理成"短版三句 + 三条绝对不能 + 两条限制"逐条与甲方确认。

### 3.2 需求整理与人工审查中的困难及解决方法

- AI 初稿存在遗漏（如"误操作撤回""商品修改"）与口径冲突（封号下架 vs 已预约不能下架）：通过逐条对照访谈来源编号（INT 编号）核对，将发现记录到 chat.txt"人工审查记录"（REV-001~REV-004），再落实到 requirements.md。
- 未确认内容（如判违规撤回后的恢复目标）标明"待确认"，未擅自写成已确认。

### 3.3 使用 AI 整理需求的作用与局限

- 作用：快速将访谈口语转化为结构化需求，保持编号与 10 字段一致，减少机械整理工作，便于逐条追踪来源。
- 局限：可能遗漏隐含需求、难以自行判断状态矛盾、会把不明确的口径直接写成正式需求；因此必须由人工逐条核对访谈与任务书依据，未确认内容标注"待确认"。
